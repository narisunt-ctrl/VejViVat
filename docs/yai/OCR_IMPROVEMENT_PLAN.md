# แผนพัฒนา OCR ฉลากยา: แพทย์ยืนยัน, วัดผลเทียบ baseline และเก็บข้อมูลตาม PDPA

สถานะ: แผน · ปรับ 2026-10-29 ตามแนวทางเจ้าของโปรเจ็ค · ผู้ร่าง: Claude

## 1. ขอบเขต

**ทำตอนนี้**
1. **แพทย์หรือเภสัชกรยืนยันข้อมูลยาที่ยายกรอกหรือยืนยันมาแล้ว** เป็นชั้นตรวจที่สองต่อจากยาย
2. **ใช้ baseline เป็นเกณฑ์เทียบ** ทุกครั้งที่ปรับปรุง เช่น เปลี่ยนจากโมเดลในเครื่องเป็น API, เปลี่ยนรุ่นโมเดล หรือเพิ่มขั้น AI ตรวจสอบ ต้องวัดเทียบกับ baseline ชุดเดียวกันก่อนตัดสินใจ
3. **ออกแบบการเก็บข้อมูลให้เป็นไปตาม PDPA**

**ยังไม่ทำ:** การฝึกหรือปรับโมเดลจากข้อมูลที่ตรวจแล้ว (ดูข้อ 7 สำหรับอนาคต)

กฎที่ไม่เปลี่ยน: **ระบบไม่สร้างวิธีใช้ยาหรือการแจ้งเตือนจาก OCR ที่ยังไม่ได้ตรวจ**

## 2. ที่มาของแนวทาง

จากเจ้าของโปรเจ็ค: นำทางการถ่ายรูป · ไม่บังคับขอบฉลาก (กล่อง กระปุก แคปซูล ยาต้ม) · ยายตรวจข้อความ · Typhoon OCR 1.5 คู่กับ PaddleOCR · benchmark (CER, ชื่อยา, ส่วนประกอบ, ขนาด, เวลา, ค่าใช้จ่าย) พร้อมเก็บรูปต้นฉบับและที่มาของข้อมูล · รันในเครื่องเมื่อไม่มี key · ใช้เฉพาะโมเดลที่ไม่ติดลิขสิทธิ์เชิงพาณิชย์ · prompt ตรวจสอบหลัง OCR (กำลังเขียน) · **แพทย์ยืนยันอีกชั้น** · **เทียบ local กับ API** · **ฐานข้อมูลตาม PDPA**

จาก Claude (ข้อเสนอ): ตัววัดข้อมูลที่ OCR แต่งขึ้น · ให้สองเอนจินตรวจกันเอง · ค้นด้วยเลขทะเบียน อย.

## 3. ขั้นแพทย์ยืนยัน

### ขั้นตอน
```
ยายถ่ายรูป ─► OCR ─► (AI ตรวจสอบ) ─► ยายตรวจ/แก้/ยืนยัน ─► รายการรอแพทย์ ─► แพทย์ยืนยัน หรือ แก้ หรือ ส่งกลับ
                                       PATIENT_REPORTED                   CLINICIAN_VERIFIED
```

- แพทย์เห็นเฉพาะยาของผู้ป่วยที่ให้ความยินยอมกับคลินิกนั้นแล้ว (ใช้ระบบความยินยอมรายคลินิกที่มีอยู่ `ConsentGrant` ขอบเขต `MEDICINES`)
- หน้าตรวจของแพทย์แสดงสามอย่างคู่กัน:
  1. **รูปต้นฉบับ** ซูมได้
  2. **ข้อความที่ OCR อ่าน** พร้อมป้ายเอนจินและช่องที่น่าสงสัย
  3. **ค่าที่ยายยืนยัน**
- แพทย์ทำได้ทีละช่อง ดังนี้
  - **ยืนยัน**
  - **แก้** ต้องใส่เหตุผลสั้น ๆ
  - **ส่งกลับให้ถ่ายใหม่** เช่น รูปไม่ชัด หรือไม่เห็นส่วนประกอบ
- เมื่อยืนยันครบทุกช่องที่จำเป็น ยาจะเปลี่ยนเป็น `CLINICIAN_VERIFIED` โดยบันทึก**ชื่อผู้ตรวจ เลขใบอนุญาต และเวลา**
- ปุ่ม `DEMO_REVIEW` ที่มีอยู่ตอนนี้ไม่ใช่ลายเซ็นแพทย์จริง ต้องแทนด้วยขั้นนี้ก่อนใช้กับผู้ป่วยจริง
- **ทุกการแก้ไขเก็บเป็นประวัติ ไม่เขียนทับ:** เก็บว่าใคร แก้อะไร จากค่าเดิมเป็นค่าใหม่ เมื่อไร และเพราะอะไร

### ข้อมูลที่ได้ (ใช้วัดผล ไม่ใช้ฝึกโมเดล)
บันทึกหนึ่งรายการต่อหนึ่งช่องข้อมูลต่อหนึ่งรูป:
- ค่าที่ OCR อ่าน (แยกตามเอนจิน)
- ค่าที่ยายยืนยัน
- ค่าที่แพทย์ยืนยัน
- ประเภทความผิดที่คำนวณอัตโนมัติ ได้แก่ วรรณยุกต์หรือสระหาย, ตกคำนำหน้า, **แต่งข้อมูลเพิ่ม**, ไม่อ่าน, ตัวเลขหรือหน่วยผิด, อ่านวนซ้ำ

ข้อมูลชุดนี้ใช้ทำสองอย่าง:
- **เพิ่มรูปเข้าชุด benchmark** เฉพาะรูปที่ยินยอมให้ใช้ปรับปรุงระบบ (ดูข้อ 6)
- **ดูว่ายายตรวจพลาดบ่อยแค่ไหน** คือกรณีที่ยายยืนยันว่าถูก แต่แพทย์แก้ เป็นตัวชี้ว่าต้องปรับหน้าจอตรวจของยาย

## 4. Baseline และวิธีเทียบ

### Baseline ระยะที่ 0
ตัวเลขทั้งหมดมาจาก `ocr-bench/README.md` และ `ocr-bench/results/` วัดบนรูปจำลอง 24 รูปและรูปจริง 4 รูป ด้วยการ์ดจอ Quadro M1200 4 GB

ตัววัดหลัก:
- **CER:** อัตราตัวอักษรผิด
- **ชื่อยาถูก**
- **ส่วนประกอบครบ**
- **ขนาดและหน่วยถูก**
- **ข้อความที่แต่งเพิ่ม** (Inserted)
- **ข้อความที่ไม่อ่าน** (Omitted)
- **ความแม่นของรายการส่วนประกอบ** (Ingr. precision)
- **อัตรารูปที่มีช่องข้อมูลถูกแต่งขึ้น** (Invented field)
- **เวลา** p50 และ p95
- **ค่าใช้จ่าย** ต่อ 1,000 รูป

ตารางผลอยู่ในข้อ 8 จะเติมเมื่อรัน baseline ระยะที่ 0 เสร็จ

### เกณฑ์ตัดสินว่า "ปรับปรุงแล้วดีขึ้น"
การเปลี่ยนแปลงจะใช้จริงได้เมื่อวัดบนชุดทดสอบเดียวกันแล้ว:
- ชื่อยาถูก **ไม่ลดลง**
- อัตรารูปที่มีช่องข้อมูลแต่งขึ้น และตัวเลขหรือหน่วยผิด **ไม่เพิ่มขึ้นเลย**
- CER ไม่แย่ลงเกิน 0.005
- เวลา p95 ไม่ช้าลงเกิน 20% หรือมีเหตุผลรองรับ เช่น แม่นขึ้นมาก
- **ผ่านเกณฑ์ PDPA** ในข้อ 6

ผลแต่ละครั้งเก็บไว้ใน `ocr-bench/results/<run>/` และคำนวณคะแนนรอบเก่าใหม่ได้ด้วย `run_bench.py --rescore` เมื่อเพิ่มตัววัดใหม่

## 6. การเก็บข้อมูลตาม PDPA

> ข้อมูลยาและรูปฉลากของผู้ป่วยเป็น **ข้อมูลสุขภาพ** ซึ่งถือเป็นข้อมูลส่วนบุคคลอ่อนไหวตาม PDPA โดยทั่วไปต้องได้ความยินยอมโดยชัดแจ้ง ส่วนนี้เป็นแนวทางเชิงเทคนิค ไม่ใช่คำแนะนำทางกฎหมาย ต้องให้ที่ปรึกษากฎหมายหรือ DPO ตรวจ และทำ DPIA ก่อนนำร่องกับผู้ป่วยจริง

### 6.1 ความยินยอม (แยกตามวัตถุประสงค์ ถอนได้ทุกข้อ)
| ข้อ | วัตถุประสงค์ | มีแล้วหรือยัง |
|---|---|---|
| ก | ส่งรูปให้เซิร์ฟเวอร์ของเราอ่าน | มีแล้ว (`cloudOcrConsent`) |
| ข | ให้คลินิกที่เลือกเห็นและยืนยันข้อมูลยา | มีแล้ว (`ConsentGrant`, ขอบเขต `MEDICINES`) |
| ค | นำรูปและผลตรวจไปใช้วัดและปรับปรุงระบบ (benchmark) | **ต้องเพิ่ม** ไม่ติ๊กไว้ให้ก่อน |
| ง | ส่งรูปให้ผู้ให้บริการภายนอก (API) | **ต้องเพิ่ม** และใช้เฉพาะเมื่อสัญญาและการประเมินผ่าน |

เก็บความยินยอมเป็นประวัติ: ข้อไหน เวอร์ชันข้อความใด ให้เมื่อไร และถอนเมื่อไร

### 6.2 เก็บอะไร ที่ไหน นานเท่าไร
| ข้อมูล | ที่เก็บ | ระยะเวลา (ข้อเสนอ) | หมายเหตุ |
|---|---|---|---|
| รูปฉลากต้นฉบับ | object storage เข้ารหัส บนเซิร์ฟเวอร์ในไทย | จนแพทย์ยืนยัน + 90 วัน แล้วลบ เว้นแต่ยินยอมข้อ ค | ต้องเก็บไว้ช่วงหนึ่ง เพราะเป็นหลักฐานของทุกช่องข้อมูล |
| ข้อมูลยาที่ยืนยันแล้ว | ฐานข้อมูลหลัก เข้ารหัส | ตลอดที่ใช้บริการ ลบเมื่อขอ | ผูกกับรหัสผู้ป่วยแบบนามแฝง ไม่ใช้เลขบัตร |
| ข้อความ OCR และประวัติการแก้ | ฐานข้อมูลหลัก | เท่ากับข้อมูลยา | ใช้ตรวจย้อนหลัง |
| ประวัติการเข้าถึง (ใครเปิดดูอะไร) | log ที่แก้ไม่ได้ | ตามนโยบายองค์กร เช่น 1 ปี | ใช้ตรวจสอบเมื่อมีเหตุ |
| ชุด benchmark (ยินยอมข้อ ค) | พื้นที่แยกเฉพาะทีมพัฒนา | จนกว่าจะถอนความยินยอม | ลบชื่อ, HN และใบหน้าในรูปก่อน โดยมีคนตรวจซ้ำ |
| ข้อมูลในเบราว์เซอร์ (`localStorage`, IndexedDB) | เครื่องของยาย | ชั่วคราว | ตอนนี้เป็นข้อมูลเดโมสังเคราะห์ ข้อมูลจริงต้องย้ายไปเซิร์ฟเวอร์ และมีปุ่มล้างข้อมูลในเครื่อง |

### 6.3 การควบคุม
- **สิทธิ์ตามบทบาท:** ยายหรือผู้ดูแลเห็นของตัวเอง, แพทย์เห็นเฉพาะผู้ป่วยที่ยินยอมกับคลินิกนั้น, ทีมพัฒนาเห็นเฉพาะชุด benchmark ที่ลบข้อมูลระบุตัวตนแล้ว
- **เข้ารหัส:** ระหว่างส่ง (HTTPS) และขณะเก็บ แยกกุญแจออกจากข้อมูล และเก็บ API key ที่เซิร์ฟเวอร์เท่านั้น (ทำอยู่แล้ว)
- **สิทธิของเจ้าของข้อมูล:** ขอดู ขอแก้ ขอลบ ขอรับสำเนา และถอนความยินยอม ต้องทำได้จากในแอปหรือผ่านช่องทางที่ระบุไว้
- **ผู้ประมวลผลภายนอก:** ถ้าใช้ API หรือ cloud ต้องมีสัญญาประมวลผลข้อมูล (DPA) และตรวจเรื่องการส่งข้อมูลไปต่างประเทศ
- **เหตุละเมิดข้อมูล:** มีขั้นตอนแจ้งเหตุตามที่กฎหมายกำหนด
- **ข้อมูลอย่างน้อยที่สุด:** ไม่เก็บข้อมูลที่ไม่จำเป็นต่อการยืนยันยา

## 7. อนาคต (ยังไม่ทำ)
ระบบเรียนรู้จากข้อมูลที่แพทย์ยืนยันแล้ว เรียงจากง่ายไปยาก:
1. คลังยาที่ยืนยันแล้ว ค้นด้วยเลขทะเบียน อย.
2. พจนานุกรมคำแก้ และเลือกเอนจินตามช่อง
3. ปรับ prompt ตรวจสอบ
4. ฝึกโมเดลตามรอบ

ทุกข้อต้องผ่านเกณฑ์ในข้อ 4 และได้ความยินยอมข้อ ค ก่อน การฝึก Typhoon ต้องตรวจข้อตกลงของ OpenTyphoon ก่อน

## 10. สิ่งที่ยังต้องตัดสินใจ
- ผู้ตรวจชั้นที่สองเป็นแพทย์ เภสัชกร หรือทั้งคู่ และตรวจทุกรายการหรือสุ่มตรวจ
- โฮสต์เซิร์ฟเวอร์และฐานข้อมูลที่ไหน (ในไทย ของโปรเจ็ค หรือของโรงพยาบาล)
- ระยะเวลาเก็บรูปต้นฉบับหลังแพทย์ยืนยัน
- ใช้ Typhoon API หรือไม่ ถ้าใช้ ต้องได้สัญญาแบบไหน
