# แผนพัฒนา OCR ฉลากยาแบบเรียนรู้เอง (self-evolving)

สถานะ: แผน (ยังไม่ได้ทำ) · ร่าง 2026-10-29 · ผู้กำหนดแนวทาง: เจ้าของโปรเจ็ค · ผู้ร่าง: Claude

## 1. เป้าหมาย

ทุกครั้งที่ยายสแกนยา แล้วยายและแพทย์ตรวจความถูกต้อง ระบบจะเก็บผลการตรวจไว้เรียนรู้ว่าส่วนไหนถูก ส่วนไหนผิด และผิดแบบไหน
จากนั้นนำความรู้นี้กลับไปทำให้การสแกนครั้งถัดไปแม่นขึ้นเอง โดยมีด่านทดสอบและคนอนุมัติก่อนนำการเปลี่ยนแปลงไปใช้จริงทุกครั้ง

กฎที่ไม่เปลี่ยน: **ระบบไม่สร้างวิธีใช้ยาหรือการแจ้งเตือนจาก OCR ที่ยังไม่ได้ตรวจ** ไม่ว่าระบบจะเรียนรู้ไปมากแค่ไหน

## 2. ที่มาของแนวทาง

แนวทางจากเจ้าของโปรเจ็ค (ทำแล้ว):
- นำทางการถ่ายรูป เพราะยายไม่รู้ว่าถ่ายครบหรือยังตอนถือกล้อง
- ไม่บังคับให้เห็นขอบฉลาก เพราะบรรจุภัณฑ์มีหลายแบบ เช่น กล่อง กระปุก แคปซูล ยาต้ม
- แสดงข้อความที่อ่านได้ให้ยายตรวจ แก้ หรือสั่งอ่านใหม่
- ใช้สองเอนจินคู่กัน: Typhoon OCR 1.5 สำหรับความแม่นภาษาไทย และ PaddleOCR PP-OCRv5 สำหรับความเร็วและควบคุมระบบเอง
- benchmark ที่วัด CER, ชื่อยา, ส่วนประกอบ, ขนาดและหน่วย, เวลา และค่าใช้จ่าย พร้อมเก็บรูปต้นฉบับและที่มาของข้อมูลทุกช่อง
- รันในเครื่องเมื่อไม่มี key และเลือกเฉพาะโมเดลที่สัญญาอนุญาตให้ใช้เชิงพาณิชย์ได้ (Typhoon 1.5 2B, Apache-2.0)

แนวทางจากเจ้าของโปรเจ็ค (แผนนี้):
- ขั้น AI ตรวจสอบหลัง OCR ด้วย prompt ที่เจ้าของโปรเจ็คกำลังเขียน
- ให้ยายตรวจ แล้วให้แพทย์ตรวจอีกชั้น
- สรุปผลถูกและผิดให้ AI เรียนรู้เอง

                                                                                  │

     ┌──────────────┬────┴─────────┬──────────────────┬───────────────────┐
     ▼              ▼              ▼                  ▼                   ▼
 คลังยาที่ยืนยัน  สถิติความผิด   ชุดทดสอบ prompt     ชุดข้อมูลฝึกโมเดล      ชุด benchmark
 (ระดับ 1)       (ระดับ 2)      (ระดับ 3)           (ระดับ 4)             (โตขึ้นเอง)

## 5. ระดับความน่าเชื่อถือของข้อมูล

| ระดับ | ใคร | ใช้ทำอะไร |
|---|---|---|
| `UNVERIFIED` | OCR | แสดงเป็นร่างเท่านั้น |
| AI ตรวจแล้ว | prompt ตรวจสอบ | ชี้ช่องที่น่าสงสัยให้คนดู ไม่ใช่คำตอบจริง |
| `PATIENT_REPORTED` / `CAREGIVER_REPORTED` | ยายหรือผู้ดูแล | สัญญาณการแก้ไข ใช้นับสถิติได้ **ห้ามใช้เป็นคำตอบสำหรับฝึก** |
| `CLINICIAN_VERIFIED` | แพทย์หรือเภสัชกร (ลงชื่อจริง) | **คำตอบจริง** สำหรับคลังยา ชุดทดสอบ และชุดฝึก |

ระบบมีระดับ `CLINICIAN_VERIFIED` อยู่แล้วใน `src/domain/yai/models.ts` แต่ตอนนี้ใช้เฉพาะปุ่มเดโม (`DEMO_REVIEW`)
ข้อมูลระดับ `DEMO_REVIEW` ห้ามเข้าวงจรเรียนรู้

## 6. ข้อมูลที่ต้องบันทึก (feedback log)

บันทึกหนึ่งรายการต่อหนึ่งช่องข้อมูล (ชื่อยา ส่วนประกอบ ขนาด ฯลฯ) ต่อหนึ่งรูป:

| ฟิลด์ | ตัวอย่าง |
|---|---|
| `imageSha256`, `photoId` | อ้างถึงรูปต้นฉบับใน IndexedDB หรือที่เซิร์ฟเวอร์ |
| `field` | `name` / `ingredient` / `strength` / `registrationNo` / `usage` |
| `ocr` | ค่าที่แต่ละเอนจินอ่านได้ พร้อมชื่อเอนจิน รุ่นโมเดล ค่าความมั่นใจ และตำแหน่งบรรทัด |
| `aiCheck` | ผลจาก prompt ตรวจสอบ (ผ่าน / สงสัย / เหตุผล) และเวอร์ชันของ prompt |
| `patientValue` | ค่าที่ยายยืนยันหรือแก้ |
| `clinicianValue` | ค่าที่แพทย์ยืนยัน พร้อมผู้ตรวจและเวลา |
| `errorType` | ประเภทความผิด (ดูข้อ 7) คำนวณอัตโนมัติจาก `ocr` เทียบกับ `clinicianValue` |
| `consentTraining` | ยินยอมให้นำไปฝึกหรือไม่ (แยกจากความยินยอมให้อ่านรูป) |

## 7. ประเภทความผิดที่ใช้เรียนรู้

| รหัส | ความหมาย | ตัวอย่างจาก benchmark |
|---|---|---|
| `TONE_VOWEL` | วรรณยุกต์หรือสระหาย/เพี้ยน | ขมินซิน → ขมิ้นชัน |
| `CHAR_SWAP` | อักษรคล้ายสลับกัน | ขมิ้นผJ → ขมิ้นผง |
| `PREFIX_DROP` | ตกคำนำหน้า | ชาตุอบเชย → ยาธาตุอบเชย |
| `HALLUCINATION` | แต่งข้อมูลที่ไม่มีบนฉลาก | ส่วนประกอบวิตามินบนกล่องอโรคา |
| `OMISSION` | ข้อมูลมีบนฉลากแต่ไม่อ่าน | ไม่อ่าน "ขมิ้นชัน" บนกล่อง |
| `NUMBER_UNIT` | ตัวเลขหรือหน่วยผิด | 500 → 50, มก. → มล. |
| `LOOP` | อ่านซ้ำวนไม่จบ | 口 口 口 … |

`HALLUCINATION` และ `NUMBER_UNIT` เป็นความผิดร้ายแรง และมีน้ำหนักสูงสุดในด่านทดสอบ

## 8. ระบบเรียนรู้ 4 ระดับ

### ระดับ 1: คลังยาที่แพทย์ยืนยันแล้ว
- เก็บข้อมูลยาที่ `CLINICIAN_VERIFIED` ผูกกับเลขทะเบียน อย. (เช่น G 447/41), ชื่อ และลายนิ้วมือของรูป (perceptual hash)
- สแกนครั้งถัดไป ถ้าเจอเลขทะเบียนหรือรูปที่ตรงกัน ระบบจะ**เสนอ**ข้อมูลจากคลังพร้อมป้าย "ข้อมูลนี้แพทย์เคยยืนยันแล้ว" และยายต้องกดยืนยันว่าเป็นกล่องเดียวกัน
- ค่าที่ OCR อ่านได้ต่างจากคลัง ให้แสดงเป็นจุดที่ต้องดู ไม่เขียนทับเงียบ ๆ

### ระดับ 2: เรียนรู้จากรูปแบบความผิด (ไม่ต้องฝึกโมเดล)
- พจนานุกรมคำแก้: เก็บคู่คำว่าอ่านผิดเป็นอะไร และคำที่ถูกคืออะไร ใช้ระยะห่างของตัวอักษรเสนอคำที่ใกล้ที่สุดจากคลังชื่อยาและสมุนไพรที่ยืนยันแล้ว
- เลือกเอนจินแยกตามช่อง: จากสถิติความผิด เช่น ช่องชื่อยาเชื่อ Typhoon และช่องตัวเลขเชื่อ PaddleOCR เมื่อสองเอนจินอ่านไม่ตรงกัน ให้ถามคน
- ให้สองเอนจินตรวจกันเอง: คำที่ Typhoon อ่านได้ แต่ PaddleOCR ไม่เห็นอะไรใกล้เคียง ให้ติดป้าย "อาจแต่งขึ้น" ซึ่งแก้ปัญหา `HALLUCINATION` โดยตรง

### ระดับ 3: ปรับ prompt ตรวจสอบ
- เคสที่แพทย์แก้ แต่ AI ตรวจสอบบอกว่า "ผ่าน" จะกลายเป็นชุดทดสอบของ prompt
- ทุกเวอร์ชันของ prompt ต้องรันกับชุดทดสอบนี้ก่อนใช้ และเก็บเลขเวอร์ชันไว้ในบันทึกทุกครั้ง
- ใช้ตัวอย่างที่ยืนยันแล้วและคล้ายกันมาประกอบการตรวจ (few-shot) ได้ แต่ต้องวัดว่าไม่ทำให้แต่งข้อมูลเพิ่มขึ้น

### ระดับ 4: ฝึกโมเดลตามรอบ (เมื่อมีข้อมูล `CLINICIAN_VERIFIED` หลายร้อยถึงหลายพันรูป)
- **PaddleOCR**: ตัดรูปเป็นทีละบรรทัดตามตำแหน่งที่ PaddleOCR คืนมาอยู่แล้ว (`rec_polys`) จับคู่กับข้อความที่แพทย์ยืนยัน แล้วฝึก `th_PP-OCRv5_mobile_rec` เพิ่ม (Apache-2.0 ทำได้)
- **Typhoon 2B**: ฝึกแบบ LoRA ได้ แต่ต้องตรวจข้อตกลงของ OpenTyphoon ก่อน เพราะข้อตกลงห้ามนำผลจาก Typhoon ไปใช้ฝึก AI (ในที่นี้คำตอบมาจากแพทย์ ไม่ได้มาจาก Typhoon แต่ควรให้ฝ่ายกฎหมายยืนยัน)
- โมเดลใหม่ทุกตัวต้องผ่านด่านทดสอบในข้อ 9

## 9. ด่านทดสอบ (benchmark gate)

การเปลี่ยนแปลงทุกอย่าง ไม่ว่าจะเป็นคลังยา พจนานุกรมคำแก้ prompt หรือโมเดล ต้องผ่านด่านนี้ก่อนใช้จริง:

1. รันกับ **ชุดทดสอบที่ล็อกไว้** ซึ่งเป็นรูป `CLINICIAN_VERIFIED` ประมาณ 20% ที่ไม่เคยนำไปฝึกหรือปรับระบบ แบ่งตามผู้ป่วยและตามยี่ห้อ เพื่อไม่ให้รั่วไปปนกับชุดฝึก
2. เงื่อนไขผ่าน (ปรับตัวเลขได้):
   - ชื่อยาถูก **ไม่ลดลง**
   - อัตรา `HALLUCINATION` และ `NUMBER_UNIT` **ไม่เพิ่มขึ้นเลย**
   - CER ไม่แย่ลงเกิน 0.005
   - เวลา p95 ไม่ช้ากว่าเดิมเกิน 20%
3. ผ่านแล้วต้องให้**คนกดอนุมัติ** ระบบไม่เลื่อนเวอร์ชันขึ้นใช้เอง
4. เก็บทุกเวอร์ชันพร้อมผล benchmark และย้อนกลับได้ทันที

เป้าหมายระยะยาว (บนรูปจริงจากมือถือ):
- ชื่อยาถูก ≥ 95%
- `HALLUCINATION` < 1% ของช่องข้อมูล
- ตัวเลขและหน่วยผิด = 0 ในชุดทดสอบ
- เวลา p95 < 15 วินาที

## 10. ความเป็นส่วนตัวและกฎหมาย

- **ความยินยอม 2 ข้อแยกกัน**: (ก) ส่งรูปให้เซิร์ฟเวอร์อ่าน ซึ่งมีอยู่แล้ว และ (ข) นำรูปและผลตรวจไปพัฒนา AI ซึ่งต้องเพิ่ม ยายถอนความยินยอมได้ และเมื่อถอน ต้องลบข้อมูลออกจากชุดฝึกรอบถัดไป
- ลบข้อมูลส่วนบุคคลในรูปก่อนเข้าชุดข้อมูล เช่น ชื่อหรือ HN บนสติกเกอร์ร้านยา หรือใบหน้า โดยให้คนตรวจซ้ำ
- เก็บชุดข้อมูลฝึกที่เซิร์ฟเวอร์ที่ควบคุมสิทธิ์การเข้าถึง ไม่เก็บในเบราว์เซอร์ และไม่ส่งให้ Typhoon API (ข้อตกลงของ API อนุญาตให้ SCB 10X นำรูปไปฝึกโมเดลได้)
- ต้องผ่านการตรวจ PDPA และจริยธรรมการวิจัยก่อนใช้กับผู้ป่วยจริง
- ใช้เฉพาะโมเดลที่ใช้เชิงพาณิชย์ได้ ดู `docs/yai/THIRD_PARTY_NOTICES.md`

| **2** | ระดับ 2: พจนานุกรมคำแก้ เลือกเอนจินตามช่อง และให้สองเอนจินตรวจกัน | ข้อมูลจากระยะที่ 1 | ลดคำเพี้ยนและข้อมูลที่แต่งขึ้น |
| **3** | ด่านทดสอบอัตโนมัติ (ข้อ 9) และหน้าอนุมัติเวอร์ชัน | ชุดทดสอบที่ล็อกไว้ | เปลี่ยนระบบได้อย่างปลอดภัย |
| **3** | ระดับ 3: ชุดทดสอบ prompt จากเคสที่แพทย์แก้ | ข้อมูลจากระยะที่ 2 | prompt ดีขึ้นอย่างวัดผลได้ |
| **4** | ระดับ 4: ฝึก PaddleOCR (และ Typhoon หากข้อตกลงอนุญาต) | ข้อมูลหลายร้อยถึงหลายพันรูป และตรวจกฎหมาย | โมเดลที่เก่งฉลากยาไทย |

## 12. สิ่งที่ยังต้องตัดสินใจ

- ผู้ตรวจชั้นที่สองเป็นแพทย์ เภสัชกร หรือทั้งคู่ และตรวจทุกรายการหรือสุ่มตรวจ
- ชุดข้อมูลฝึกเก็บที่ไหน (เซิร์ฟเวอร์ของโปรเจ็ค หรือของโรงพยาบาลหรือคลินิก)
- จะนำคลังยาที่ยืนยันแล้วมาแชร์ข้ามผู้ป่วยได้หรือไม่ (ข้อมูลยาไม่ใช่ข้อมูลส่วนตัว แต่รูปอาจมี)
- ใช้ prompt ตรวจสอบกับโมเดลตัวไหน: ในเครื่อง หรือผ่าน API ที่ผ่าน PDPA แล้ว
